# Blast Radius — development notes

Working notes for anyone continuing this project (including future-me). For the
user-facing overview and GitHub Pages setup, see `README.md`.

Current version: **v0.9.1** (pre-v1). Knowledge base: **2026.10.22**.

---

## What this is

A browser-only tool for reasoning about Microsoft Entra (Azure AD) application
permissions, directory roles, group membership, and delegated-admin (GDAP)
relationships. It answers: if an app's credential is stolen, what's the blast
radius, can it escalate to Global Admin, and what compensating controls help.

No backend, no network calls. All analysis happens in the browser. The tool
never uploads anything — this is a core property, not an incidental one, and it
should stay true (no analytics, no telemetry, ever).

Prompted by the Oct 2026 ConnectWise/SkyKick vendor-credential incident
(Huntress writeup).

## Repo layout (source vs. build)

The tool is authored as three source files and **built** into self-contained
single-file HTML. Do not hand-edit the built files; edit source and rebuild.

```
app.source.html   source: markup + CSS (references kb.js / app.js)
kb.js             source: knowledge base (permissions, roles, controls, data)
app.js            source: engine + rendering + wiring
build.py          build script -> produces the two shipping files
fixtures/         frozen sample inputs for tests (see "Testing")
test/             test runners
```

The source markup is deliberately named `app.source.html`, **not** `index.html`,
so it can't be confused with the deployed public build (see next section).
`build.py` reads `app.source.html` + `kb.js` + `app.js`.

Build outputs (generated by `python3 build.py`, written to the output dir):

```
blast-radius-public.html   single-app "before you consent" ONLY. Public-safe.
blast-radius-local.html    full tool (all 3 modes). Offline/self-hosted ONLY.
```

For GitHub Pages, deploy the **public build** as `index.html` (copy/rename
`blast-radius-public.html` to `docs/index.html`, or repo-root `index.html` —
pick one folder in Pages settings). The **local build must never be hosted on a
public URL** (it has a `DO NOT host publicly` comment baked into its `<head>` as
a reminder). A Pages site is public even from a private repo on the free tier.

> On the two "index.html" meanings: there is only one `index.html` that matters,
> and it is the **deployed public build** on Pages. The source markup is named
> `app.source.html` precisely so it is never mistaken for that. So: edit
> `app.source.html` -> run `build.py` -> deploy the generated
> `blast-radius-public.html` as `docs/index.html`. Never deploy the local build.

## The three modes

1. **Single app** (public-safe) — pick/paste the permissions an app requests,
   get a three-state Global-Admin verdict (direct / conditional / no known path),
   blast radius, detection reality, ranked controls, vendor questions. All
   synthetic input; nothing sensitive.
2. **Whole tenant** (offline only) — paste a read-only export of every service
   principal. Transitive takeover resolution: app-credential backdoor chains,
   group membership / role-assignable-group paths, ownership paths. Ranked app
   list, rollup, exportable report.
3. **Partner / MSP** (offline only) — paste a read-only GDAP export. Maps which
   customer tenants a partner compromise unlocks and which partner security
   groups are "master keys."

The public build strips modes 2 & 3 entirely (engine, samples, and PowerShell
scripts removed via `<<<STRIP-PUBLIC-*>>>` sentinels in `app.js`, handled by
`build.py`). The shared `app.js` is null-safe (`$id`/`on`/`has` helpers) so it
runs whether or not the tenant/partner DOM exists.

## Knowledge base provenance

Escalation classifications are **derived from public research**, not invented:

- Emilien Socchi — Azure administrative tiering (the direct/indirect split)
- Maester `Test-MtHighRiskAppPermissions` (Tier-0 list + appRole GUIDs)
- SpecterOps / BloodHound edge docs (attack-path logic: AddMember/AddOwner, the
  role-assignable-group protection, app-role grant edges)
- Horizon3.ai H3-2024-0039
- Microsoft Graph permissions reference (via graphpermissions.merill.net)
- Microsoft Learn (role-assignable groups, GDAP mechanics)
- Huntress ConnectWise/SkyKick writeup (the incident + several controls)

Classification changes are **security-sensitive**: a wrong "no known path" is
worse than a wrong "exposed". The changelog lives at the top of `kb.js`
(`KB_VERSION` + comment). Bump it on any classification change so a defender can
tell whether a prior run's verdict still holds.

Key correctness nuances already baked in (don't regress these):
- `Group.ReadWrite.All` **cannot** modify role-assignable groups (Microsoft
  protection). Only RoleManagement.ReadWrite.Directory, or an existing
  owner/member, reaches them. Plain group-write over such groups => **cleared**,
  not confirmed.
- Only role-assignable groups can hold directory roles; a non-role-assignable
  group "holding GA" is impossible and must not be treated as privileged.
- PIM-eligible GA is a **distinct, gated** state (scored below standing GA), not
  flattened into "direct".
- Human owner vs service-principal owner of a privileged app are **different
  risk classes** and scored differently.

## v0.9 — what shipped this round

Detection:
- Cross-tenant credential flag (tenant-side credential on an externally-owned
  vendor SP = the SkyKick persistence pattern). Allowlist is **data**
  (`CROSS_TENANT_CRED_ALLOWLIST` in kb.js), each entry carries a reason; MS
  first-party handled separately; allowlisted hits downgrade *with reason shown*.
- PIM-eligible modeled as its own gated state.
- Ownership paths (human vs SP owner), resolved from both the SP side and the
  group/app side, matching by object id OR appId.
- Credential `source` (app registration vs service principal) surfaced.
- Credential flags are now structured `{ text, sev, why }` — every flag states
  why it fired so a reviewer can overrule it.
- "Changes since" date filter (flags only timestamped credentials; says so).

Safety:
- Crown-jewel "treat this like a password vault" banners on sensitive modes.
- "Clear data" buttons (wipe paste + results from memory).
- Blind-spot note rendered at the point of results, not just the footer.
- "No network calls — verify in dev tools" footer.
- `DO NOT host publicly` comment in the offline build head.
- Export scripts hardened: read-only emphasis, "never reads credential values",
  timestamped filenames, explicit `Remove-Item` delete reminders; now collect
  owners, PIM-eligible roles, and credential source.

Correctness:
- Sanitized **PascalCase fixtures** + `fixture.test.js`. These caught 3 real bugs
  the hand-written samples missed (PascalCase credential dates; group ownership
  expressed by appId on the group object).

## Testing

All tests are **developer** tests (Node, run from the repo). None ship in the
HTML. Pattern is golden-master / fixture: a frozen realistic input + asserted
known-good output, so any drift in a verdict or flag fails loudly.

```
node test/fixture.test.js     # loads fixtures/*.json through the real engine,
                              # asserts verdicts + flags (21 assertions)
```

Keep fixtures **realistic** (that's what caught the PascalCase bug — a too-clean
fixture tests a world that doesn't exist) and **frozen** (never edit a fixture to
make a failing test pass — that just rubber-stamps whatever the code does now).
When a fixture test fails, the question is always "did I break the code, or did
reality actually change?" — only the second justifies touching the fixture.

There are additional ad-hoc suites that were run during development (engine,
group, partner, report, DOM-smoke). A good v1 task is to move them all under
`test/` as committed files so the whole suite runs with one command.

## Roadmap / next workstream (staged, not yet done)

Highest-leverage first:

1. **Playwright test** — load both built files headless, assert zero CSP
   violations, expected verdicts on the fixture, credential flags firing.
   (Couldn't run headless in the dev environment; it's mostly packaging.)
2. **Access-package / app-role grants on non-role-assignable groups** — the one
   remaining place the tool says "conditional, can't tell" when richer export
   data could resolve it to confirmed-or-cleared.
3. **Verdict diff between two exports** — "last month this app was 'no known
   path', now it reaches GA, here's why." Drift detection is arguably more
   actionable for a scheduled MSP run than any single snapshot. Bigger — likely
   its own version.

Safety posture to preserve as features grow:
- Each new export field makes the file more sensitive. Keep the export script
  short + obviously read-only; collect the **minimum** that answers the question;
  never read credential **values**.
- Keep "no network calls" absolutely true.
- Treat KB contributions as security review (a bad classification is a silent,
  dangerous failure).
- State blind spots **where results are shown**, loudly — the most dangerous
  output is an unearned all-clear.

## Gotchas

- Source is `app.source.html`; the only `index.html` is the deployed public
  build on Pages. Don't deploy the local build. See "Repo layout" above.
